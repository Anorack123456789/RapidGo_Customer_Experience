# ADR-003: Orquestación y validación del pipeline de experiencia del cliente mediante Apache Airflow

**Estado:** Aceptado

## 1. Contexto

Durante la tercera semana de desarrollo de RapidGo Customer Experience Analytics se incorporó una capa de orquestación para coordinar las actividades posteriores al procesamiento continuo de eventos. Aunque la arquitectura implementada en la fase anterior permitía recibir información desde Kafka, procesarla mediante Spark Structured Streaming y almacenarla en el Data Lake, era necesario establecer un mecanismo que organizara las validaciones, el cálculo de indicadores y la generación de reportes.

Para atender esta necesidad se decidió incorporar Apache Airflow como herramienta de orquestación, ejecutándolo dentro del entorno Docker junto con los demás componentes del proyecto. Se configuró la versión `3.3.2` y se estableció un DAG denominado `rapidgo_customer_experience_pipeline`, encargado de coordinar las actividades del procesamiento analítico.

El flujo se estructuró en cinco tareas principales: `check_sources`, `validate_raw`, `aggregate_kpis`, `validate_curated` y `generate_report`. Estas actividades permiten verificar la disponibilidad de las fuentes, comprobar la calidad de los datos almacenados, calcular indicadores relacionados con la experiencia del cliente, validar los resultados agregados y generar reportes para su posterior consulta.

Durante la implementación también se identificaron dificultades relacionadas con la compatibilidad del esquema de los archivos Parquet y los permisos de escritura entre los contenedores de Spark y Airflow. Esto hizo necesario establecer reglas de validación coherentes con la estructura real de los datos y configurar un mecanismo automatizado para preparar los directorios compartidos antes de iniciar los servicios. Adicionalmente, se debieron corregir problemas de concurrencia en la inicialización de Kafka para asegurar la creación de particiones, y ajustar el pipeline de ingesta para garantizar el almacenamiento efectivo de la capa cruda (raw).

Adicionalmente, se planteó ampliar el workflow de GitHub Actions incorporando validaciones específicas para la importación y estructura del DAG, de manera que los cambios en la orquestación puedan comprobarse automáticamente antes de integrarse al repositorio.

## 2. Decisiones arquitectónicas

### 2.1. Incorporación de Apache Airflow para la orquestación

Se decidió utilizar Apache Airflow como herramienta para coordinar las actividades posteriores al procesamiento de eventos. Su función dentro de la arquitectura consiste en ejecutar tareas dependientes entre sí, controlar el orden de procesamiento y facilitar el seguimiento de las ejecuciones.

Airflow se ejecuta mediante un contenedor Docker basado en `apache/airflow:3.3.2`, utilizando el comando `standalone` para disponer de un entorno funcional durante el desarrollo y las pruebas locales. La interfaz web se expone mediante el puerto `8083` del equipo anfitrión.

La configuración permite mantener Airflow separado de los procesos de generación y procesamiento de eventos, evitando incorporar las responsabilidades de orquestación directamente en el productor o en el script de Spark.

2.2. Definición del DAG y sus dependencias

Se decidió implementar un DAG denominado `rapidgo_customer_experience_pipeline`, ubicado en `airflow/dags/rapidgo_pipeline.py`. Este DAG organiza el flujo de trabajo mediante cinco tareas con dependencias secuenciales:

1. `check_sources`: comprueba la disponibilidad de las fuentes de datos necesarias para iniciar el procesamiento.
2. `validate_raw`: verifica la existencia de archivos y la estructura de los datos de entrada, incluyendo las columnas requeridas y algunas condiciones básicas de calidad.
3. `aggregate_kpis`: calcula los indicadores de experiencia del cliente a partir de los datos disponibles.
4. `validate_curated`: comprueba la estructura y consistencia de los resultados agregados.
5. `generate_report`: genera los reportes correspondientes a los resultados obtenidos.

La secuencia de ejecución establecida es:

`check_sources → validate_raw → aggregate_kpis → validate_curated → generate_report`

Esta organización permite detener el flujo cuando una validación falla, evitando que las tareas posteriores trabajen con información que no cumple las condiciones establecidas.

### 2.3. Comunicación entre tareas y mecanismos de recuperación

Se decidió utilizar los mecanismos de comunicación de Airflow, incluyendo XCom, para transferir información entre las tareas del DAG cuando sea necesario. Esto permite compartir resultados de verificaciones y datos de ejecución sin depender de archivos temporales para cada intercambio.

También se configuraron mecanismos de reintento para las tareas, con el propósito de permitir nuevas ejecuciones cuando se presenten fallos temporales. Los reintentos no sustituyen las validaciones de calidad ni corrigen errores permanentes, por lo que las excepciones deben registrarse y mantenerse visibles en el historial de ejecución.

La utilización de XCom y los reintentos facilita el seguimiento de las actividades y la recuperación ante determinados errores, aunque no garantiza por sí sola que una operación externa sea idempotente o que no se generen registros duplicados al repetir una tarea.

### 2.4. Validación de los datos de entrada

Se decidió incorporar validaciones sobre los archivos Parquet almacenados en el Data Lake antes de ejecutar las agregaciones. Para ello se utiliza PyArrow, permitiendo consultar la estructura de los archivos y comprobar que contienen las columnas necesarias.

El esquema de datos utilizado en esta fase contempla los siguientes campos:

- `event_id`
- `event_type`
- `timestamp`
- `order_id`
- `customer_id`
- `rating`
- `reason`
- `channel`
- `kafka_timestamp`
- `event_time`
- `is_negative`

Entre las condiciones de validación se encuentran la presencia de las columnas requeridas, la existencia de registros, la disponibilidad del identificador del pedido, las calificaciones dentro del rango de 1 a 5, los motivos y marcas temporales válidos, y la ausencia de valores nulos en los campos temporales necesarios.

Durante las pruebas se identificó una incompatibilidad entre el esquema esperado inicialmente por el DAG y los archivos realmente generados por Spark. El código esperaba los campos `motivo` y `timestamp_ms`, mientras que los archivos Parquet utilizaban `reason` y `timestamp`. Por esta razón se ajustaron las columnas requeridas y las utilizadas en las agregaciones para mantener la correspondencia con los datos procesados.

### 2.5. Organización de las capas del Data Lake y generación de indicadores

Se decidió mantener el Data Lake como mecanismo de almacenamiento de los resultados del procesamiento, utilizando directorios diferenciados para organizar la información y facilitar su consumo por las tareas de Airflow.

La configuración utilizada por el entorno de orquestación contempla las siguientes ubicaciones:

- `datalake/raw`: directorio destinado a los datos de entrada (crudos).
- `datalake/processed`: contiene los archivos procesados que sirven como fuente para las validaciones y agregaciones.
- `datalake/curated`: almacena los resultados agregados y preparados para su consulta.
- `reports`: almacena los reportes generados por el pipeline.
- `checkpoints`: conserva los archivos de estado requeridos por los procesos que utilizan checkpoints.

Las rutas se comparten mediante volúmenes de Docker, permitiendo que los contenedores de Spark y Airflow accedan a los archivos desde sus respectivos entornos de ejecución. 

La tarea `aggregate_kpis` utiliza los datos disponibles para producir resultados analíticos relacionados con la experiencia del cliente, mientras que `validate_curated` comprueba que los resultados generados puedan utilizarse en las actividades posteriores. Finalmente, `generate_report` organiza los resultados para facilitar su interpretación.

La separación de estas ubicaciones permite distinguir los datos procesados de los resultados analíticos y los reportes, aunque la estructura de directorios no implica por sí sola que todas las transformaciones del modelo medallion se encuentren implementadas o que los datos de cada capa tengan una calidad garantizada.

### 2.6. Gestión de permisos y directorios compartidos entre contenedores

Durante la ejecución del DAG se identificó un problema de permisos cuando Airflow intentó crear directorios y escribir resultados en la ubicación `datalake/curated`. El inconveniente se originó por las diferencias entre los usuarios con los que se ejecutan los contenedores: Airflow utiliza el UID `50000`, mientras que Spark utiliza el UID `185`.

Como solución se decidió incorporar un servicio auxiliar denominado `init-permissions` en `docker-compose.yml`, basado en la imagen `alpine:3.22` y ejecutado con privilegios de administrador dentro del contenedor.

Este servicio prepara los directorios compartidos y establece los permisos necesarios antes de iniciar los componentes que los utilizan. Para ello se asigna el grupo `185` a los directorios del Data Lake y de checkpoints, se habilitan los permisos de lectura y escritura para el grupo y se configura el bit setgid en los directorios para facilitar la herencia del grupo en los archivos creados posteriormente.

Para el directorio de reportes se mantienen permisos de escritura para el usuario de Airflow, identificado con el UID `50000`.

Adicionalmente, se incorporó `group_add: ["185"]` en la configuración del servicio Airflow y se estableció `umask 0002` en los servicios correspondientes para favorecer la colaboración entre procesos que utilizan el grupo compartido.

El servicio `init-permissions` se configura como dependencia de los componentes que requieren los directorios preparados, utilizando la condición `service_completed_successfully`. De esta manera, la inicialización de permisos forma parte del procedimiento de arranque de la arquitectura y no depende exclusivamente de intervenciones manuales.

### 2.7. Ampliación de las validaciones mediante GitHub Actions

Se decidió ampliar el workflow `CI.yml` para incluir verificaciones relacionadas con la nueva capa de orquestación. Se mantiene su ejecución ante eventos `push` y `pull_request` dirigidos a las ramas `main` y `preproduccion`, además de permitir su ejecución manual mediante `workflow_dispatch`.

La configuración contempla Python 3.12 y Apache Airflow 3.3.2, utilizando el archivo de restricciones oficial de Airflow correspondiente a esa versión de Python para controlar la compatibilidad de las dependencias.

Las validaciones contempladas en el workflow son:

- Descargar el repositorio mediante `actions/checkout@v4`.
- Configurar Python 3.12 mediante `actions/setup-python@v5`, con caché de dependencias de pip.
- Instalar las dependencias del proyecto y Apache Airflow utilizando las restricciones correspondientes.
- Comprobar la sintaxis de los archivos Python mediante `python -m compileall`.
- Validar la importación del DAG utilizando `DagBag`.
- Comprobar que el DAG `rapidgo_customer_experience_pipeline` exista y contenga las cinco tareas requeridas.
- Verificar las dependencias entre las tareas del flujo de orquestación.
- Ejecutar las pruebas automatizadas mediante `pytest -v`.
- Validar la configuración de Docker Compose mediante `docker compose config --quiet`.

La incorporación de `DagBag` permite comprobar que Airflow pueda interpretar el archivo del DAG sin necesidad de iniciar los servicios de Kafka, Spark o el propio servidor de Airflow. Asimismo, la comprobación de las tareas y sus dependencias permite detectar modificaciones que alteren la estructura esperada del pipeline.

Estas verificaciones amplían el alcance de la integración continua, aunque no equivalen a una prueba de integración completa ni demuestran que el procesamiento de datos se ejecute correctamente en un entorno real.

## 3. Alternativas consideradas

**Ejecutar todas las validaciones en una única tarea.** Se decidió mantener tareas independientes para la disponibilidad de las fuentes, validación de datos, agregación, validación de resultados y generación de reportes. Esta separación facilita identificar en qué etapa ocurre un error y evita continuar el flujo cuando una condición previa no se cumple.

**Asignar permisos manualmente desde el equipo anfitrión.** Se descartó depender de comandos manuales para preparar los directorios compartidos, debido a que esta solución no garantiza que los permisos se mantengan correctamente después de recrear los contenedores. Se incorporó el servicio `init-permissions` para automatizar la preparación de los directorios.

**Validar únicamente la sintaxis del código mediante GitHub Actions.** Se decidió ampliar las verificaciones para incluir la importación del DAG y la comprobación de sus tareas y dependencias. Esta alternativa permite detectar errores estructurales en la orquestación antes de integrar cambios, aunque no sustituye las pruebas de ejecución del pipeline.

## 4. Consecuencias de las decisiones

La incorporación de Apache Airflow permite coordinar las actividades posteriores al procesamiento de eventos y establecer una secuencia controlada para verificar los datos, calcular indicadores y generar reportes. La definición de tareas independientes facilita el seguimiento de las ejecuciones y permite identificar con mayor precisión los errores que se presentan durante el flujo.

La utilización de XCom y los mecanismos de reintento proporciona herramientas para gestionar la comunicación entre tareas y responder ante fallos temporales. Sin embargo, las operaciones que escriben archivos o modifican datos deben considerar la posibilidad de ejecuciones repetidas, especialmente cuando una tarea falla después de haber realizado parcialmente su trabajo.

La validación del esquema de los archivos Parquet permite detectar diferencias entre la estructura esperada y los datos realmente generados por Spark. Esto reduce el riesgo de realizar agregaciones sobre campos inexistentes o registros que no cumplen las condiciones definidas. No obstante, las reglas de calidad deben actualizarse cuando se modifique el contrato de eventos o se incorporen nuevas variables.

La incorporación del servicio `init-permissions` permite automatizar la preparación de los directorios compartidos y reducir los conflictos de escritura entre Spark y Airflow. Esta decisión introduce una dependencia adicional durante el arranque de los servicios, por lo que su ejecución debe completarse correctamente antes de iniciar los componentes que necesitan acceder al Data Lake.

La ampliación de GitHub Actions mejora la validación del repositorio al incorporar comprobaciones específicas para la estructura del DAG. Sin embargo, el workflow no demuestra por sí solo la conectividad entre los servicios, la disponibilidad de los archivos Parquet, la correcta ejecución de las agregaciones ni la generación efectiva de reportes.

Por último, el sistema requiere pruebas adicionales de recuperación, ejecución repetida, calidad de los datos y comportamiento ante fallos controlados. Los resultados obtenidos durante las pruebas locales deben documentarse mediante registros de Airflow, archivos generados y resultados de las validaciones, evitando presentar como garantías características que todavía no han sido comprobadas.
