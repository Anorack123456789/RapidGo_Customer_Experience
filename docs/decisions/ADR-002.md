# ADR-002: Implementación del procesamiento de eventos y analítica en tiempo real

**Estado:** Aceptado  

## 1. Contexto

Durante la segunda semana de desarrollo de RapidGo Customer Experience Analytics se implementó el flujo de procesamiento de eventos de retroalimentación de los clientes, utilizando un productor en Python, Apache Kafka como sistema de mensajería, PySpark Structured Streaming para el procesamiento continuo y un Data Lake para almacenar los resultados.

El productor genera eventos sintéticos con información sobre el pedido, su calificación, el motivo de la retroalimentación y la marca temporal. Cada evento se envía al tópico `rapidgo.customer_feedback`, utilizando `order_id` como clave del mensaje, de acuerdo con la decisión establecida en el ADR-001. La generación de eventos se realiza aproximadamente cada dos segundos, con calificaciones aleatorias entre 1 y 5 y motivos como `demora`, `daño`, `perdida`, `excelente`, `normal` y `fraude`.

Para procesar estos datos, se desarrolló el script `src/streaming.py`, encargado de consumir los mensajes desde Kafka, interpretar su contenido JSON, aplicar reglas de clasificación de alertas y almacenar los eventos procesados en formato Parquet. Adicionalmente, se incorporó una segunda consulta de streaming para calcular métricas agrupadas por motivo y ventanas temporales, con el propósito de facilitar el análisis de las quejas y detectar situaciones que requieren atención.

Durante la implementación también se identificaron inconvenientes relacionados con la compatibilidad de las dependencias de Spark y Kafka, la resolución de paquetes Maven y la persistencia del estado de las consultas. Por este motivo, se establecieron criterios de ejecución y almacenamiento orientados a mantener la compatibilidad del entorno y permitir la recuperación del procesamiento después de una interrupción.

Además, se incorporó el workflow `CI.yml` mediante GitHub Actions para automatizar validaciones básicas del repositorio. El flujo se ejecuta ante cambios enviados a las ramas `main` y `preproduccion`, ante Pull Requests dirigidos a esas ramas y mediante ejecución manual. Su propósito es detectar errores de sintaxis, ejecutar las pruebas automatizadas y comprobar que la configuración de Docker Compose pueda interpretarse correctamente antes de integrar cambios.


## 2. Decisiones arquitectónicas

### 2.1. Integración del productor con Kafka mediante un tópico de eventos

Se decidió mantener `rapidgo.customer_feedback` como tópico de intercambio entre el productor y el consumidor, utilizando mensajes JSON con los campos `order_id`, `rating`, `motivo` y `timestamp_ms`. El campo `order_id` se utiliza como clave del mensaje, conservando la decisión de particionamiento documentada en el ADR-001.

El productor utiliza `localhost:9092` para conectarse desde el entorno anfitrión, mientras que el consumidor de Spark utiliza `kafka:19092`, dirección prevista para la comunicación dentro de la red de contenedores Docker. Esta configuración requiere que los listeners y puertos anunciados por Kafka sean compatibles con ambos puntos de acceso.

La creación del tópico y la configuración del broker corresponden al entorno de Kafka y no al script de procesamiento. Por tanto, el productor y Spark dependen de que el tópico exista o de que el broker permita su creación automática.

### 2.2. Ejecución de Spark dentro del entorno Docker

Se decidió ejecutar el procesamiento utilizando el entorno de contenedores del clúster de Spark, en lugar de depender directamente del entorno Python instalado en Windows. El trabajo se ejecuta mediante `spark-submit` desde el entorno de Spark, lo que permite utilizar las dependencias y la conectividad disponibles dentro de la arquitectura Docker.

Esta decisión reduce la dependencia de configuraciones específicas del sistema anfitrión, como `HADOOP_HOME` y `winutils.exe`, cuando son necesarias para ejecutar determinadas operaciones de Hadoop desde Windows. También permite centralizar la configuración del entorno de procesamiento y mantener una mayor consistencia entre las ejecuciones.

### 2.3. Compatibilidad de las dependencias de Spark y Kafka

Se decidió alinear la versión del conector de Kafka con las versiones de Spark y Scala disponibles en el clúster. La configuración utilizada para la ejecución contempla el paquete:

`org.apache.spark:spark-sql-kafka-0-10_2.13:4.2.0`

Esta decisión se tomó después de identificar un error `NoSuchMethodError` durante la inicialización de la lectura de Kafka, relacionado con el uso inicial de una dependencia compilada para Scala 2.12 y una versión diferente de Spark.

La dependencia debe mantenerse compatible con la versión real del clúster para evitar conflictos de clases y problemas al gestionar los offsets y los metadatos de Structured Streaming.

### 2.4. Procesamiento de eventos y clasificación de alertas

Se decidió aplicar las reglas de clasificación directamente sobre los eventos recibidos mediante PySpark, incorporando las columnas `event_time`, `nivel_alerta` y `causa_alerta`.

Las reglas de clasificación establecidas son las siguientes:

- Las calificaciones iguales o inferiores a 2 generan `ALERTA_CRITICA`, independientemente del motivo, con la causa `CALIFICACION_BAJA`.
- Las calificaciones iguales a 3 generan `ALERTA_CRITICA` cuando el motivo es `demora`, `daño` o `perdida`, con la causa `MOTIVO_GRAVE`.
- Las demás calificaciones iguales a 3 generan el nivel `ATENCION`.
- Las calificaciones de 4 y 5 se clasifican como `NORMAL`.

La clasificación permite separar los eventos que requieren atención de aquellos que no activan alertas críticas. No obstante, los motivos generados por el productor son aleatorios y el motivo `fraude` no forma parte de la regla que clasifica como crítica una calificación de 3; este comportamiento corresponde a la lógica implementada durante esta fase.

### 2.5. Almacenamiento de eventos y alertas en el Data Lake

Se decidió almacenar los resultados del procesamiento en formato Parquet, separando los eventos procesados de los eventos que generan algún nivel de alerta.

Las rutas definidas son:

- `/opt/spark/work-dir/datalake/eventos_procesados`: almacena todos los eventos procesados.
- `/opt/spark/work-dir/datalake/alertas`: almacena los eventos cuyo nivel de alerta es diferente de `NORMAL`.

Las escrituras se realizan en modo `append` para incorporar nuevos registros a los datos existentes. El uso de Parquet proporciona una estructura columnar adecuada para posteriores consultas analíticas; sin embargo, el script no define explícitamente una estrategia de particionamiento de archivos ni una configuración específica de compresión.

Para conservar los datos fuera del ciclo de vida de los contenedores, se decidió utilizar montajes de volúmenes en Docker que vinculan el directorio local `./datalake` con la ruta de almacenamiento del contenedor y `./docs` con el directorio destinado, entre otros recursos, a los checkpoints.

### 2.6. Gestión de checkpoints y recuperación de las consultas

Se decidió mantener ubicaciones de checkpoint independientes para las dos consultas de Structured Streaming, de manera que el procesamiento de eventos y el cálculo de métricas dispongan de sus propios metadatos de recuperación.

Las rutas utilizadas son:

- `/opt/spark/work-dir/docs/checkpoints/eventos`
- `/opt/spark/work-dir/docs/checkpoints/metricas`

Los checkpoints permiten registrar el progreso de las consultas y facilitan su recuperación después de una interrupción, siempre que se conserven los archivos requeridos y se mantengan compatibles la consulta y su configuración.

Durante la resolución del conflicto de dependencias fue necesario eliminar los checkpoints anteriores para iniciar una ejecución limpia. Esta medida implica descartar el progreso registrado en el estado eliminado y, por tanto, debe utilizarse únicamente cuando se acepta reiniciar la consulta. La presencia de checkpoints no constituye, por sí sola, una garantía de procesamiento *exactly-once* de extremo a extremo, especialmente al combinar `foreachBatch` con escrituras Parquet en modo `append`.

### 2.7. Cálculo de métricas mediante ventanas temporales

Se decidió utilizar una segunda consulta de streaming para calcular indicadores agrupados por motivo y ventana temporal. La consulta aplica un *watermark* de 30 segundos y ventanas de 20 segundos, calculando dos indicadores: `total_quejas`, que cuenta los eventos recibidos para cada motivo, y `criticas`, que cuenta los eventos clasificados como `ALERTA_CRITICA`.

Los disparadores se configuran de manera independiente: la consulta que almacena eventos se ejecuta cada 5 segundos, mientras que la consulta de métricas se actualiza cada 10 segundos. La salida de las métricas se dirige a la consola, lo que facilita la observación de los resultados durante las pruebas.

El indicador `total_quejas` representa el total de eventos del grupo y no exclusivamente las quejas, dado que también se contabilizan los registros con motivos como `excelente` y `normal`. Esta distinción deberá mantenerse al interpretar los indicadores durante el análisis de resultados.


### 2.8. Validación automatizada mediante GitHub Actions

Se decidió incorporar el workflow `CI.yml` para automatizar comprobaciones del código y de la configuración del repositorio. El workflow, denominado `CI RapidGo`, se activa cuando se realiza un `push` hacia las ramas `main` o `preproduccion`, cuando se abre o actualiza un Pull Request dirigido a cualquiera de estas ramas y cuando se inicia manualmente mediante `workflow_dispatch`.

El trabajo `validar` se ejecuta en un entorno `ubuntu-latest` e incluye los siguientes pasos:

- Descargar el contenido del repositorio mediante `actions/checkout@v4`.
- Configurar Python 3.12 mediante `actions/setup-python@v5`, con caché de dependencias de pip.
- Instalar las dependencias declaradas en `requirements.txt`.
- Comprobar la sintaxis de los archivos Python ubicados en `producer`, `spark` y `test`, mediante `python -m compileall producer spark test`.
- Ejecutar las pruebas automatizadas con `pytest -v`.
- Validar la configuración de Docker Compose mediante `docker compose config --quiet`.

La decisión busca establecer una validación repetible para detectar errores básicos antes de integrar cambios en las ramas principales. La compilación comprueba la sintaxis de los archivos incluidos en las rutas indicadas, `pytest` ejecuta las pruebas disponibles y la validación de Docker Compose comprueba que la configuración sea interpretable. Estos pasos no equivalen a una prueba de integración de extremo a extremo: el workflow descrito no inicia explícitamente los servicios de Kafka y Spark ni verifica por sí solo que los eventos atraviesen el pipeline correctamente. La efectividad de la integración continua debe confirmarse mediante ejecuciones reales del workflow y sus resultados.

## 3. Alternativas consideradas

**Ejecutar Spark directamente desde Windows.** Se descartó como alternativa principal la ejecución desde el entorno anfitrión, debido a las diferencias de configuración y dependencias que pueden presentarse entre Windows y el entorno de ejecución del clúster. Se priorizó la ejecución dentro de Docker para mantener la consistencia del entorno.

**Utilizar una única consulta para eventos y métricas.** Se mantuvieron dos consultas independientes, una destinada al almacenamiento de los eventos procesados y las alertas, y otra orientada al cálculo de métricas. Esta separación permite configurar disparadores y checkpoints distintos para cada propósito.

**Utilizar una dependencia de Kafka compilada para otra versión de Scala.** Esta opción se descartó después de identificar errores de compatibilidad durante la ejecución. Se decidió utilizar el conector correspondiente a Scala 2.13 y Spark 4.2.0, de acuerdo con la versión declarada para el clúster.

**Mantener todos los resultados en una única ubicación de almacenamiento.** Se optó por separar los eventos procesados de las alertas para facilitar su identificación y permitir análisis posteriores diferenciados.

**Validar el repositorio únicamente de forma manual.** Se optó por incorporar un workflow de GitHub Actions que ejecuta comprobaciones de sintaxis, pruebas automatizadas y validación de Docker Compose ante cambios en las ramas `main` y `preproduccion`, en Pull Requests dirigidos a ellas o mediante ejecución manual. Esta alternativa reduce la dependencia de que cada colaborador recuerde ejecutar las comprobaciones localmente, aunque no reemplaza las pruebas de integración del pipeline completo.

## 4. Consecuencias de las decisiones

Las decisiones adoptadas proporcionan una base para generar eventos sintéticos, procesarlos de forma continua, identificar situaciones críticas y almacenar los resultados para análisis posteriores. Asimismo, la separación de las consultas de streaming facilita la observación de los eventos y de las métricas, mientras que el uso de checkpoints y volúmenes persistentes contribuye a conservar el estado de las consultas y los archivos producidos entre ejecuciones.

Estas decisiones también introducen dependencias que deben gestionarse durante las pruebas. La conectividad del sistema depende de la configuración de los listeners de Kafka, la ejecución requiere mantener compatibles las versiones de Spark, Scala y el conector de Kafka, y la recuperación de las consultas depende de la conservación y compatibilidad de sus checkpoints. De igual forma, las reglas actuales de clasificación deben revisarse si se modifica el catálogo de motivos o se requiere incluir nuevos criterios de criticidad.

El sistema todavía requiere validaciones específicas de rendimiento y recuperación antes de establecer garantías cuantitativas sobre la latencia, la estabilidad del throughput o la semántica de entrega. Los resultados observados durante las pruebas locales deben documentarse como mediciones de ejecuciones concretas y no como características garantizadas de la arquitectura.

La incorporación de GitHub Actions añade una comprobación automatizada para los cambios del repositorio: el workflow valida la sintaxis de Python, ejecuta la suite de pruebas y verifica la configuración de Docker Compose. Esto mejora la repetibilidad de las verificaciones antes de integrar cambios; sin embargo, la cobertura y el alcance de la validación dependen de las pruebas existentes y de que las ejecuciones del workflow finalicen correctamente. El workflow actual no demuestra por sí solo la conectividad de Kafka, el procesamiento en Spark ni la persistencia efectiva de los datos.

## 5. Problemas y medidas correctivas registradas

Durante la implementación se presentaron dos dificultades principales:

1. **Incompatibilidad de dependencias:** se identificó un error `NoSuchMethodError` durante la inicialización del procesamiento Kafka-Spark. Se ajustó el conector a `spark-sql-kafka-0-10_2.13:4.2.0` y se eliminaron los checkpoints anteriores para reiniciar la consulta con un estado limpio.
2. **Fallos en la descarga de dependencias Maven:** se presentaron errores `SSLHandshakeException: certificate_unknown` y `Content Length mismatch`. Como medida correctiva, se eliminó la caché temporal de Ivy del contenedor y se estableció la ruta `/tmp/.ivy2` mediante la configuración `spark.jars.ivy` en el comando de ejecución.

Estas medidas permitieron abordar los problemas identificados durante la configuración, aunque la validación final debe apoyarse en ejecuciones reproducibles y registros del entorno.

## 7. Estado final

Las decisiones de esta fase establecen la estructura del pipeline de procesamiento de eventos de RapidGo, desde la generación de retroalimentación sintética hasta su transformación, clasificación, almacenamiento y agregación temporal. El diseño permite continuar con la validación del comportamiento de las alertas y los indicadores, además de preparar la arquitectura para las siguientes actividades de pruebas, análisis y documentación.

Las garantías de rendimiento, recuperación y entrega de extremo a extremo permanecen sujetas a validaciones adicionales y no se consideran demostradas únicamente por la configuración descrita en este ADR.

Además, se incorporó una base de integración continua mediante GitHub Actions para automatizar comprobaciones de sintaxis, pruebas automatizadas y validación de la configuración de Docker Compose. La ejecución satisfactoria de estas validaciones deberá confirmarse en los registros del workflow; su definición no constituye por sí sola evidencia de que todas las pruebas hayan pasado ni de que el pipeline completo se encuentre validado de extremo a extremo.
